# מה השתנה בתכ"ם

מטלת בית: POC שמאפשר לקרוא הוראת תכ"ם בלי להוריד קובץ, ולראות מה השתנה בין מהדורה למהדורה.

## הבעיה

אתר הוראות תכ"ם מפרסם כל הוראה, הודעה וטופס כקובץ Word. למי שעובד לפי ההוראות, כמו חשבים, אנשי רכש וספקים, זה יוצר שתי בעיות:

- כדי לקרוא סעיף אחד צריך להוריד קובץ ולפתוח אותו ב-Word.
- כשהוראה מתעדכנת אין דרך נוחה לדעת מה השתנה. ל-295 מתוך 418 ההוראות באתר יש יותר ממהדורה אחת, והאתר מציג את המהדורות הקודמות כרשימת תאריכים. מי שרוצה לדעת מה השתנה מוריד שני קבצים ומשווה ביד.

למה כדאי לפתור: הוראה מחייבת מיום התוקף שלה. מי שממשיך לעבוד לפי הנוסח הקודם, למשל של מועד תשלום או של שיעור ריבית, טועה בלי לדעת. לכן צריך לראות מה בדיוק השתנה, ולא רק שהיה עדכון.

בסוף כל הוראה יש "טבלת שינויים" שהמחבר ממלא ביד: שורה לכל סעיף שהשתנה, בלי הנוסח הקודם. בהוראה 1.4.3 הטבלה מציינת למהדורה 6 שישה סעיפים. ההשוואה ב-POC מראה שינויים גם בסעיפים 2.9.3, 3.8 ו-3.11, שלא מופיעים בה.

## הפתרון

המערכת עובדת על מדגם של 10 מסמכים עם 21 מהדורות, משלושה פרקים של התכ"ם, ונותנת שני דברים:

- קריאה בלי הורדה. כל מהדורה מוצגת בתוך הדף כ-PDF, עם מספרי הסעיפים והעיצוב של המקור.
- מה השתנה. בוחרים מהדורה קודמת ורואים כל פסקה ששונתה, נוספה או הוסרה, עם מספר הסעיף שלה. בפסקה ששונתה מסומנות המילים שיצאו והמילים שנכנסו.

שתי דוגמאות שאפשר לבדוק מיד בלשונית "מה השתנה": בהודעה 3.1.1.1 ריבית החשב הכללי ירדה מ-5% ל-4.75%, ובהוראה 1.4.3 בין מהדורה 5 ל-6 שונו 26 פסקאות, נוספו 10 והוסרו 8.

## הרצה

נדרש Node.js בגרסה 22.12 ומעלה. המדגם כבר נמצא בתיקייה `data/sample`.

```bash
npm install
npm run build
npm start
```

האתר עולה בכתובת http://localhost:3000. הפקודה `npm run build` בונה את ה-client לקבצים סטטיים, ו-Express מגיש גם אותם וגם את ה-API. לכן יש process אחד ו-port אחד.

- פיתוח: `npm run dev` מריץ שני processes, את Express ב-port 3000 ואת Vite ב-port 5173. נכנסים לכתובת http://localhost:5173.
- בדיקות: `npm test`.
- לפני commit: `npm run check`, שמריץ type check, בדיקות ו-build.
- הגדרות: משתני סביבה עם ברירות מחדל, מפורטים בקובץ `.env.example`. אין סיסמאות או מפתחות.

## ארכיטקטורה ותכנון טכני

לכל מהדורה נשמרים שלושה קבצים:

- קובץ ה-docx: המקור מהאתר, להורדה.
- קובץ ה-pdf: להצגה בתוך הדף.
- קובץ ה-txt: להשוואה. שורה לכל פסקה, עם מספר הסעיף בתחילתה.

ההכנה נעשית פעם אחת, ולא בכל בקשה:

- הפקודה `npm run fetch-sample` מורידה מהאתר את קבצי ה-Word שרשומים בקובץ `sample.config.json`.
- הפקודה `npm run convert` מריצה את LibreOffice על כל קובץ Word ומפיקה ממנו את ה-PDF ואת הטקסט.

בזמן ריצה השרת לא פותח קבצי Word. הוא מגיש את ה-PDF, וכשמבקשים לראות מה השתנה הוא קורא שני קבצי טקסט ומשווה ביניהם.

- הקובץ `manifest.json` הוא רשימת המסמכים והמהדורות. במדגם קטן הוא מחליף בסיס נתונים.
- הקובץ `shared/types.ts` מחזיק את ה-types שהשרת וה-client חולקים. כך תשובת ה-API והקוד שקורא אותה מוגדרים במקום אחד.

טכנולוגיות: TypeScript בשרת וב-client, Node.js עם Express, React עם Vite, הספרייה diff להשוואת מערכים, Vitest ו-supertest לבדיקות, ו-LibreOffice להמרה.

```
shared/types.ts   the types shared by server and client
server/           Express API: config, catalog, text (parsing), compare, app (routes), index
client/src/       React: catalogue (home), side tree, document page, reading view, changes view
scripts/          data preparation: fetch-sample.ts, convert.ts
data/sample/      manifest.json + a docx, a pdf and a txt file for every edition
tests/            Vitest: text, compare, api
```

```
GET /api/health
GET /api/documents
GET /api/documents/:id
GET /api/documents/:id/editions/:number/pdf     (and /docx for the original file)
GET /api/documents/:id/compare?from=5&to=6
```

איך ההשוואה עובדת:

1. כל שורה בקובץ הטקסט הופכת לאובייקט עם מספר הסעיף ועם הנוסח, למשל `{ label: '1.5.9', text: '...' }`.
2. משווים את שני המערכים לפי הנוסח בלבד ולפי הסדר, כמו diff של שורות. מספר הסעיף לא משתתף בהשוואה. לכן כשמוסיפים סעיף, והסעיפים שאחריו מקבלים מספר חדש, הם לא נחשבים שינוי.
3. בין פסקאות שיצאו לפסקאות שנכנסו באותו מקום מחפשים זוגות דומים, כאלה שלפחות חצי מהמילים שלהם משותפות. זוג כזה מוצג כפסקה ששונתה, עם סימון המילים. כל השאר מוצג כפסקה שנוספה או הוסרה.

## בדיקות

הפקודה `npm test` מריצה 44 בדיקות על הלוגיקה ועל ה-API, מול המדגם האמיתי. שתיים מהן משוות את התוצאה למה שהמסמכים אומרים על עצמם: הסעיפים שבטבלת השינויים של הוראה 1.4.3, והריבית שירדה מ-5% ל-4.75%.

מקרי הקצה שנבדקים:

- מהדורה ריקה, מהדורה מול עצמה, ופסקה שמופיעה פעמיים.
- סעיף שרק המספר שלו השתנה.
- סימני כיוון בלתי נראים ש-Word שם ליד מספרים. בלי לנקות אותם, שתי פסקאות שנראות זהות היו נחשבות שונות.
- תאריך בטבלה, כמו 19.09.2024, שנראה כמו מספר סעיף.
- מסמך או מהדורה שלא קיימים, בקשה בלי שתי מהדורות שונות, וכתובת שבורה.
- קובץ שרשום ב-`manifest.json` ולא נמצא בדיסק. הכתובת `/api/health` מחזירה 503 עם שם הקובץ, וההשוואה מחזירה שגיאה מסודרת בלי שהשרת קורס.

## החלטות הנדסיות ואיכות

### השיקולים המרכזיים

- הצגה ב-PDF. דפדפן לא מציג קובץ Word, ולכן כל מהדורה מומרת ל-PDF. כך המסמך נראה כמו המקור, עם מספרי הסעיפים, בכל דפדפן.
- המרה פעם אחת, ולא בכל בקשה. מהדורה שפורסמה לא משתנה, ולכן ה-PDF והטקסט נוצרים בשלב ההכנה, והשרת נשאר קטן ובלי LibreOffice.
- השוואה צפויה. לאותן שתי מהדורות מתקבלת תמיד אותה תוצאה, ולכן אפשר לבדוק אותה בבדיקות.
- היקף קטן. 10 מסמכים, קובץ במקום בסיס נתונים, ומעט ספריות.

### מה בחרתי לא לממש

- כל האתר. ה-POC עובד על 10 מסמכים. לאתר המלא צריך קליטה מתוזמנת של מהדורות חדשות ובסיס נתונים.
- טבלאות. טבלה מושווית שורה אחרי שורה, כטקסט, ולא כטבלה. לכן גם טבלת השינויים של המחבר לא מוצגת כטבלה לצד ההשוואה. זה השיפור הראשון שהייתי מוסיף למוצר.
- פסקה שעברה מקום. היא מוצגת כפסקה שהוסרה ופסקה שנוספה.
- סוגריים הפוכים. בהוראה 1.4.3 יש שם של תקנות שהסוגריים שלו שמורים הפוך בקובץ המקור, וכך הם מוצגים גם ב-PDF וגם ברשימת השינויים.
- חיפוש בתוך הטקסט של ההוראות. באתר החיפוש עובד רק על שם המסמך, מילות המפתח והתיאור.
- סיכום השינויים בעזרת LLM. מודל שפה יכול לנסח תקציר מתוך רשימת השינויים, אבל לא להחליף את ההשוואה עצמה.
- בדיקות ל-React. הבדיקות מכסות את השרת ואת ה-API, ולא את המסכים.

### השינוי החשוב ביותר לתחזוקה ולגדילה

לחשב את ההשוואות מראש ולשמור אותן ב-PostgreSQL, במקום לחשב בכל בקשה ולהחזיק את הרשימה בקובץ. מהדורה שפורסמה לא משתנה, ולכן כל השוואה מחושבת פעם אחת, כשמהדורה חדשה נקלטת. באתר יש 1,127 מסמכים, ועל אותן טבלאות אפשר להוסיף חיפוש בטקסט ועמוד של כל השינויים בחודש האחרון.

## פריסה ותפעול

### השינויים הנדרשים

- שלושה services במקום process אחד: ה-API ב-container, ה-client כקבצים סטטיים ב-S3 עם CDN, ומנוע ההמרה עם LibreOffice כ-worker נפרד שרץ כ-job מתוזמן.
- אחסון: קבצי ה-docx, ה-PDF והטקסט ב-S3, ורשימת המסמכים וההשוואות ב-PostgreSQL במקום `manifest.json`.
- תהליך CI/CD ב-GitHub Actions: type check, בדיקות, build, בניית Docker image, deploy ל-staging, בדיקת תקינות, ואז deploy ל-production. גם ה-secrets ומשתני הסביבה מנוהלים שם.
- ניטור: בדיקת ה-health וה-logs של ה-API ושל ה-worker, עם התראה כשמשהו נכשל.

### אימות תקינות הפריסה

- בדיקת health: הכתובת `/api/health` מחזירה 200 רק אם רשימת המסמכים נטענה וכל הקבצים שרשומים בה קיימים. אחרת היא מחזירה 503 עם שמות הקבצים החסרים.
- בדיקת smoke אחרי deploy: השוואה אחת עם תוצאה ידועה. בהודעה 3.1.1.1, בין מהדורה 53 ל-54, 5% הופך ל-4.75%.

### תרחיש כשל

ה-worker של ההמרה נכשל באמצע, למשל כי האתר לא ענה או כי LibreOffice נכשל על קובץ אחד. מהדורה חדשה נשארת בלי PDF או בלי טקסט, ואי אפשר לקרוא או להשוות אותה.

- זיהוי: בדיקת ה-health מחזירה 503 עם שמות הקבצים החסרים, וה-monitoring מתריע. ה-deploy נעצר, והגרסה הקודמת ממשיכה לעבוד.
- אבחון: ה-log של ה-worker אומר מה נכשל. כבר היום הסקריפטים מדפיסים את זה: את הסטטוס שהאתר החזיר ואת הכתובת, או את שמות הקבצים ש-LibreOffice לא המיר.
- תיקון: מריצים שוב את ההמרה, והיא ממירה רק את מה שחסר.

ה-PDF במדגם הופק ב-LibreOffice ולא ב-Word, ולכן העימוד קרוב למקור אבל לא תמיד זהה לו.
